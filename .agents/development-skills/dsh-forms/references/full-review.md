# 用户要求完整检查Skill配置表

目标是让用户看到配置覆盖范围、当前值和待确认项，而非只填缺项。先识别“完整”指当前YAML的所有字段，还是该Skill支持的全部配置能力；未限定时先覆盖当前配置，再核对Skill声明的可选/条件参数，标明范围，不默认穷举未知能力。

## 1. 核对配置来源与覆盖

读取目标Skill说明、用户当前配置、样例及现有ui/form.yaml。需要核对全部支持字段时，继续看明确的配置schema/校验器和相关执行入口，不扫描无关业务源码。准备简短字段清单：字段路径、当前值、单位/类型、必填或可选、适用条件、默认行为及来源。无法从定义或代码确认的项标未知，不自行填补。

至少区分：

- 当前YAML已有字段：是否全被表单覆盖，是否被JSON回退包含。
- 支持但当前缺省的字段：执行器省略时的行为；不要把未知默认写成null，null与省略可能语义不同。
- 条件字段与互斥方案：哪些当前生效，哪些仅属于其他方法/模式。
- 用户输入、自动派生值、身份/版本与执行确认字段：都可列出核对，但不让用户靠手填伪造预检证据，也不由Agent凭推测补值。

普通样例不一定包含全部可选项；渲染成功只证明该输入可显示，不能据此宣称“Skill所有参数已覆盖”。

## 2. 提供完整且可编辑的审阅入口

当前文件全字段检查优先直接`create --config <当前.yaml> --brief`。自动推断不附加业务when条件，因此能展开当前文件已有分支；JSON回退需提示具体位置，不能将其遗漏不查。用户要求填写时返回新的pending请求，不把已提交只读回执当作填写入口。

如定制表单有条件隐藏，完整`read --id <req-id>`检查`form`、`values`、`activeValues`：values保留的分支与activeValues当前生效分支分别呈现。页面复制摘要/简报通常只含生效分支，不足以完成全量核查。

用户要查看全部支持参数，而当前文件不含某些项时：先列出缺省字段及来源；需要可编辑完整界面时，维护独立的审阅配置/声明式表单，保留源文件。互斥方案用条件分支或分别提供配置，不拼成业务校验必然失败的“大而全”输入。引擎没有`--all`/`--show-hidden`或自动枚举业务schema的选项，不能编造命令。新增/改版表单布局时遵守项目界面设计规则，沿用同任务已确认选择。

## 3. 用户提交后检查变化再交接

读取完整记录核对所有保留值，再取生效配置交给业务校验。对照源配置报告值变化、清空、显式增删、分支切换及当前不生效的保留值；不能把条件投影造成的字段缺失误报为用户删除。Study模式按保存流程读取，不等待临时请求的提交状态。

执行原Skill提供的离线校验；若其所谓校验会连接设备、创建run或有其他副作用，先按真实作用和任务授权处理，不能因名称叫validate就视为纯读取。交付用三项说明：已覆盖范围、仍待确认/未覆盖项、下一步业务使用入口。不要凭表单提交宣布业务执行成功。
