# PPT · SlideWise

## 先策划，再制作

新任务先读[内容策划流程](references/content-planning.md)。首次回复的重点是**跟用户讨论材料的目的与方向**，不是询问配色、字体或立即制作幻灯片。已有材料先读再问；用两三句话复述理解，只问真正影响方向的一两个问题。不要要求用户填写完整策划表。

首轮是轻量意图选择：每次只问1–2个关键问题，每题尽量给a/b/c三个直观选项，并允许自定义文字，不追问技术细节。优先确定用途和方向；体量可以粗选“5–10分钟短报告 / 10–30分钟常规报告 / 长篇内容”，不问精确页数、不由时长硬换算页数。已明确的字段跳过，配色字体留后续。选项设计与可点击表单见[轻量询问](references/intake.md)。

**两个正式审查节点：R1内容逻辑稿 → R2实际PPT样例。**尤其在前期讨论少、材料或偏好不足时，两者都不能跳过。用途选择不是内容批准；内容批准也不是视觉批准。不额外设一轮固定“主线审批”，必要问题可在讨论中澄清。详细交付与反馈格式见[两个审查节点](references/review-gates.md)。

用户回答用途、听众、时长或“1a、2a”后，整理证据、主线、逐页内容并自查，**把可读的内容逻辑稿完整呈现在聊天中或提供可打开文档，停在R1等反馈**。不能以“方向明确了”直接生成整套。R1认可后才制作并导出1–2页有代表性的实际样例PPT，停在R2；样例认可后再展开整套。用户已有确认材料、确认模板或明确要求跳过时复用其授权，不能自行猜测用户已批准。

内容阶段按需读取策划参考，不提前加载视觉图库或渲染实现，不调用视觉专家来代替逻辑策划。

按以下六步推进，随任务复用已有结论，不机械逐轮提问：

| 步骤 | 中间成果 | 推进条件 |
|---|---|---|
| 1. 目的与方向 | 受众、用途、预期理解/决策、范围和表达重心 | 目的和方向已由用户说明或确认；尚有歧义就继续讨论 |
| 2. 材料与证据 | 事实/判断/假设/缺口分类，来源编号 | 关键缺口有处理办法，不能用编造补齐 |
| 3. 汇报主线 | 核心问题、组织顺序及其理由 | 纳入R1审查稿，不单独增加固定审批 |
| 4. 逐页内容 | 实际正文、依据、素材和前后关系 | 不接受只有栏目名称的大纲，不为凑页数造内容 |
| 5. 内容审查 | 具体问题修订后形成可读内容逻辑稿 | R1：用户审查目的、逻辑链、核心内容和证据缺口 |
| 6. 样例与整套 | 1–2页实际样例PPT→用户反馈→整套 | R2：用户审查密度、布局、配色和风格；通过后展开 |

用户已给完整主线/定稿且明确要求直接制作时，简要复述采用的方向后使用现成内容，不重复索要同一确认。明确要求跳过讨论可执行，但注明假设与待确认项；不得自行把“简单任务”当作免策划理由。缺事实仍不能编造。测试样例smoke.yaml只用于用户明确的流程试跑，不替代真实任务内容。

策划过程中只输出当前阶段需要用户判断的内容，不把六步一次性倾倒给用户。较长任务用[策划稿模板](assets/planning-template.md)保存到当前文稿目录的planning.md；简单任务可留在对话中。模板是内部工作底稿，不是给用户的问卷。

## 0.2 生产能力（优先入口）

进入制作、接收用户编辑或复用模板时，读取[生产版式与检查](references/production.md)。优先用analysis/comparison/patent-card语义YAML直接create，图片传本地文件路径；不要把大量坐标和base64写进模型上下文。示例见[production.example.yaml](config/production.example.yaml)。

新增命令：read默认精简图片；原始源文件用read --full --output deck.json。diff --from N核对用户改动；check检查结构及可选事实清单；render生成逐页预览并复用未变化页；stage记录实际审查依据；template-capture/template-apply复用已确认对象布局。完整参数用CLI help。

read简版不能直接save。export会检查硬结构错误并缓存相同成品。浏览器预览与PPTX渲染均应检查，明确真实使用的渲染器。

## 编辑与交付

- R1通过后先调用CLI生成单独的1–2页样例稿件，导出真实PPTX并给预览链接；R2通过后再展开整套。用户可改字、移动和缩放对象，在“修改意见”栏留言，点击“保存给Agent”，回原聊天继续；不轮询、不自动唤醒。
- 用户保存后read最新稿件。布局改动直接调整；结论、数据、顺序改变时同步内容稿，并检查相关页面。用户改变汇报目的时先更新任务理解和主线，不沿旧方向继续美化。
- 首版采用简单版式。视觉专家按用户对当前任务的选择执行，不自动委派；已确认的结论、数字、限定条件不能为了排版擅自删改。
- 导出可编辑PPTX并检查页数、文字、图片、表格和中文字体；未看真实PowerPoint渲染不能宣称像素一致。复杂模板导入、自动视觉美化和画板批注不在首版范围。

## 入口

从项目根运行 `node packages/ppt-slidewise/cli.mjs <command>`；其他cwd使用该文件的绝对路径。公开参数/字体/样例见 [使用说明](references/workflow.md)。依赖和构建属于一次性安装工作，普通制作不重复安装。

```text
create --id <新的英文短名> --input <计划.yaml>
read --id <已有ID>
patch --id <ID> --revision <刚读取的revision> --input <修改.json>
save --id <ID> --revision <刚读取的revision> --input <完整deck.json>
open --id <ID>
export --id <ID>
```

- create返回ID、revision和URL；记住这些值，重试时先read，不另建重复稿。
- create不覆盖；patch/save必须带最新revision，冲突先重新读取并合并，不盲目改revision重试覆盖。
- read返回精简deck、revision、用户note（图片仅元数据）；完整deck用read --full --output。patch按slideId/elementId更新指定属性，保留其余元素。
- 导出返回本机PPTX路径；必须实际文件存在才交付。URL是查看/编辑入口，不等于已导出。
- 用户让打开时调用宿主可用浏览器入口，否则只返回可点击URL。不改系统默认浏览器。
- 稿件在`data/ppt-slidewise/<id>/`，旧版在history，素材嵌入deck，不依赖全局演示目录。用户私有材料不进Git。
- 字体首选微软雅黑正文/黑体标题；支持等线、楷体、仿宋及本机确认的Light变体。字体文件不随包复制，迁移前检查目标机器。未知变体不能当作已安装。导出写入Latin/eastAsia/cs名称，不等于嵌入字体。
- 首版固定16:9；不自动修改用户现有全局SlideWise页面、不调用Zemax。

## 简单旧版输入（仅供已有稿件）

title优先准确表达本页核心信息；证据不足时可以是问题或带限定的结论，不强造肯定句。body、rows、steps三种主体选一，body可配image（PNG/JPEG/WebP base64 data URL）。来源用source。图表必须标明是真实数据还是合成示意。技术试跑可用 [smoke.yaml](config/smoke.yaml)。

批量改布局或替换图片可read后写完整deck，再save。普通改字/坐标优先patch。
