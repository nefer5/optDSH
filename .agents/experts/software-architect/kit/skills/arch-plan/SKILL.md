# 分级“先设计后计划”

目标：结构决策先于代码，但流程重量与任务相称。**简单任务不走复杂流程。** 判定依据与模板在 `{{RESOURCE_ROOT}}/`（入口 `START.md`）；项目约束看 ARCHITECTURE.md 与 `.agents/architecture.toml`，二者与本次用户指示优先于本技能。

## 第一步：定级（必做，30 秒内）

依据 `{{RESOURCE_ROOT}}/principles.md` 的“任务分级”：

| 级别 | 信号（满足任一即归入该级或更高） |
|---|---|
| L0 | 1–2 个文件；不新增模块、入口、公共接口、配置键；做法明确 |
| L1 | 3–5 个文件；已有模块内新增文件；新增配置键；改模块内部接口 |
| L2 | 新模块/子系统/入口；跨层或公共接口变更；新增依赖库；预计 >5 个文件、跨多轮会话或需要多人/多 Agent 分工 |

用一句话写出级别和理由。拿不准取较低级别，并写出升级条件。

## L0：立即退出本流程

直接实现 → 运行相关测试或检查 → 交付时一句话说明落点（例如“已改 `app/config.py` 的默认超时为 30，相关测试通过”）。不写落点表、不写计划、不追加扩展建议。

## L1：回复内落点表

1. 搜已有实现（函数名、配置键、错误文本），确认复用还是新增。
2. 在回复中给 5–10 行落点表：`路径 | 所属层/模块 | 新增/修改 | 职责`，附依赖影响一行、验证命令一行（格式见 `{{RESOURCE_ROOT}}/templates/change-plan.md`）。
3. 用户已授权实施则列表后直接做；否则等确认。不写计划文件。
4. 完成后跑表中的相关验证命令并对照落点自查；不要求每轮或每项任务运行架构扫描。Git提交前由pre-commit检查暂存区一次，用户要求深入审查时用arch-review。

## L2：设计 → 确认 → 计划 → 执行 → 审查

### 1. 勘察

读 AGENTS.md、README、ARCHITECTURE.md、`.agents/architecture.toml`；看顶层目录和主要入口；搜已有实现；需要依赖证据时运行 `arch_scan.py`（全量不加 `--changed`）。没读过的文件不当作已检查。

### 2. 分段设计

按“目标与档位 → 落点总览 → 依赖方向与接口 → 取舍与验证”分段交给用户，每段几行即可。

- **每轮最多问 3 个问题**，每个问题给推荐默认（用户可回复“按默认”）。
- 已知答案不重复问；低风险、可逆的选择写成明确假设继续。
- 参考 `{{RESOURCE_ROOT}}/patterns.md` 选最小结构；新增抽象层需要至少两个真实使用者或已确认的近期需求。
- 作为子 Agent 不能直接提问时，把合并问题与推荐默认交回主会话。

### 3. 用户确认

拿到对设计的明确确认（或明确的“直接做”授权）后再写计划。未确认前不写业务代码；可做只读勘察。

### 4. 写计划文件

- 位置：`.agents/architecture.toml` 中 `[plan] dir`，缺省 `.agents/plans/`；项目另有计划或运行目录约定时以项目为准。
- 文件名：`YYMMDD-<slug>.md`（例如 `261002-export-service.md`）。
- 内容按 `{{RESOURCE_ROOT}}/templates/plan.md`：目标、设计摘要、任务列表；每个任务写**文件落点、接口签名、验证步骤、完成标记**。
- 计划写到文件、接口和验证为止，**不预写完整代码**。

### 5. 按任务执行

- 按顺序做；每个任务完成后立即运行它的验证步骤，通过后勾选完成标记。
- 偏离计划（新增文件、改接口、需要新模块）时先更新计划并说明，必要时重新确认，不悄悄扩大范围。
- 测试先行只用于行为明确的核心逻辑；胶水代码、配置和一次性脚本不强制。
- 只有任务多且相互独立时才并行委派子 Agent；委派时交接落点表、接口和约束。

### 6. 收尾自查

全部任务完成后对照已确认落点、依赖方向及相关验证结果自查，在计划文件中标记状态。架构扫描按需要取证；提交阶段由Git pre-commit检查暂存区一次，不再自动续轮或要求--record。用户明确要求深入审查时调用arch-review。

## 相比 superpowers 有意省略的

- 不强制建工作树或分支；按项目约定执行。
- 不强制所有代码 TDD；只对行为明确的核心逻辑测试先行。
- 计划不预写完整代码，只写落点、接口与验证。
- 不要求每个任务派一个子代理；只有任务多且独立时才并行委派。
- 不要求 L0/L1 任务走头脑风暴或写设计文档。

## 交付

先给结论和成果入口（落点表、计划文件路径、改动范围），再写验证结果；区分“已实现 / 已运行检查 / 推断”。未完成项与需要主会话决定的点集中列出。
