# 架构审查与整改入口

用户明文请求或需要解释 Git 提交检查时使用，不在每轮结束自动触发。默认只读；用户明确要求整改时，先给证据与方案，再按 arch-plan 的级别及已有授权实施，不重复确认已获授权的事项。

## 最短流程

1. 明确范围：本次提交、当前未提交改动、指定模块或全项目；读项目 AGENTS、ARCHITECTURE.md、`.agents/architecture.toml`（存在时）及相关真实代码。
2. 如已有 Git pre-commit 检查结果，先复用结果，不为调用技能再扫描一次。扫描是证据工具，按需要运行，不是审查的必经步骤：
   - 本次待提交内容：`python {{KIT_ROOT}}/scripts/arch_scan.py --staged`。
   - 当前未提交改动：`python {{KIT_ROOT}}/scripts/arch_scan.py --changed`。
   - 全量：去掉范围参数。
3. 判断是否涉及模块归属、入口、依赖方向、公共接口、重复实现或业务硬编码。局部修改无需结构调整时，简短说明并结束。
4. 需要深入时按宿主委派 software-architect；宿主无该角色时由主 Agent 执行，并说明不是独立审查。按任务读取 `{{RESOURCE_ROOT}}/START.md` 与相关语言清单，不通读参考包。
5. 交付：结论、证据来源、最多3–5个问题、最小整改顺序。区分违反约束/设计取舍/个人习惯及已检查/推断。扫描发现只是线索；疑似密钥只报脱敏位置，不把误报当确定泄露。
6. 用户要求整改时保留业务、数据、接口及他人修改，按已确认方案实施并做相关验证；仅审查时不顺手修改代码。

## 扫描结果与退出码

0 = 无 error；1 = 有 error 级线索；2 = 配置/用法/内部错误（检查未完成）。Git 提交入口只报告、不阻断，人工审查需要判断误报。没有扫描不宣称确定性检查通过。

不需要 --record，也不维护自动提醒状态。旧 --record 仅供历史手工审计兼容；本流程不使用它。Git hook 不启动模型、不委派专家、不自动整改；由当前 Agent 阅读输出，或用户明文调用本技能。

## 宿主入口

| 宿主 | 深入审查 |
|---|---|
| Codex / Claude Code / OpenCode | 已分发的 software-architect 专家；不可用时主 Agent 审查 |
| DSH | expert_software_architect 工具或软件架构专家预设 |

不为凑检查次数增加测试，不为让扫描变绿删功能、放宽阈值或重构无关代码。
