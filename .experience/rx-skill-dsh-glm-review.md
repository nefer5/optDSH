# Rx Skill：DSH + GLM 实测复盘

核验日期：2026-09-27。适用环境：本项目官方DSH 0.1.5-rc.3、Standard、glm-5.3-flash、Windows。本文记录原因与边界；行为规则维护在[Rx Skill](../.agents/skills/optdsh-rx-collection-efficiency/SKILL.md)及[执行参考](../.agents/skills/optdsh-rx-collection-efficiency/references/execution.md)。

证据：[表单评测](../runs/skill-eval/260927-02/report.html)、[真实分析报告](../runs/rx-agent/260927-01/report.html)、[审计](../runs/rx-agent/260927-01/audit.json)、[分段计时](../runs/rx-agent/260927-01/timing-summary.json)。历史包不改写。本轮只优化Skill与文档，未重新调用GLM或Zemax，不能把静态校验当行为复测。

## 1. 确定性公式不能保护被Agent误改的输入

现象：GLM将Detector Rectangle半宽8.2×15 mm算为246 mm²（应为492），又拟用它替换已确认的参考面积1020 mm²。监督器在执行前纠正；真实追迹未使用错误的246。

已证实：执行器用4xy计算源面积，用配置中的参考面积计算归一化功率；它只校验参考面积为正，无法判断Agent改写该字段是否有研究依据。错误发生在配置解释和准备阶段，不是确定性公式把面积算错。

处理：用户提交/明确确认的Study参数优先；源面积、探测器面积、参考面积分开列；派生值由脚本计算和复算。缺少定义应列待确认，不猜默认值。1020仅为此次确认值，不提升为通用常量。旧错误草稿保留在研究run 260927-08，不能当后续默认配置。

## 2. HTTP服务存活不等于ZOS连接忙

已核对[service.py](../packages/optics/src/optdsh_optics/service.py)：桥接服务保存快照，真实操作调用短时worker；工作台每3秒读取缓存，刷新才采集。服务启动也有一次采集，所以“只手动连接”并非完整描述。快照显示通常不占ZOS，但显式刷新、探测、保存、分析仍可能同时到达。

当前[Rx CLI](../.agents/skills/optdsh-rx-collection-efficiency/scripts/scan.py)同时使用端口存活门禁和项目内tx-pilot.lock。端口门禁迫使停启服务，扩大了本来只需协调API操作的冲突范围；项目内锁又不能覆盖另一项目。不能简单删门禁就宣称跨环境安全。

用户选择的方向：业务Skill保持独立，工作台保留缓存；由公共ZOS层按API实例管理短时排他访问，busy时保留缓存并明确状态，不污染成永久采集错误。后续实现需核对所有连接路径、退出/异常释放、锁持有到真实连接释放的时序、同实例竞争与不同实例并行。未接入共同协议的第三方脚本仍无法保证互斥。**这部分尚未实现，3081门禁仍存在。**

## 3. Windows Job生命周期与权限是两件事

已证实：官方dsh-subprocess-local的runner在直接命令退出后仍等Job为空。Agent内Start-Process启动常驻3081，其后代进程可仍在同一Job，导致工具不返回。完全权限解除访问限制，不能解除Job的等待语义；调大超时只是延后，超时终止也不是脱离托管。

本次只读预检脚本约15秒，停/预检/恢复的包装命令却约201.8秒；外层监督器接管生命周期才继续。它证明临时处理有效，不证明自主运行或运行时修复。当前Skill不再要求Agent在短命令中恢复常驻服务；未来优先通过实际API互斥消除普通扫描的服务停启需求，而不是让每个Skill绑定工作台管理器。

## 4. 执行完成、恢复安全与结果可信分别验收

9点×20000光线扫描脚本34.6秒，扫描循环20.532秒；独立中心点脚本15.5秒、循环1.531秒。两次主模型检查及副本关闭通过，归一化复算误差约1.39e-17。

但中心归一化SPAD效率从0.201416%变成0.032469%，相差6.203倍；审计明确repeatabilityAccepted=false。相同声明seed不足以证明实际随机流相同；未记录命中数与权重方差，不能断言是噪声、几何或顺序bug。GLM曾给出过强几何解释，已被监督纠正。源功率、revision等不同的历史run只作线索，不作受控对比。

后续：在用户授权的少量追迹范围内，固定模型/源准备/采样，比较独立点与网格内点，并记录实际种子、命中统计和顺序；没有证据前保留未知。不要为了漂亮的报告扩大试验或改写旧结果。

## 5. 效率瓶颈与会话归属需有原生证据

表单四轮真实调用中，两次创建32.74/38.83秒，提交读回28.73秒，pending检查16.44秒；工具仅约0.58–0.63秒，主要时间在模型。保留create/read --brief、一次检查后交还用户、执行参考按需加载，避免把每次参数收集升级成Zemax检查。样例值会预载，不能称“空白表单”；清空保留null，源文件不覆盖。

真实分析四阶段已计墙钟合计约14.2分钟、模型约9.3分钟，不含人审间隔。只读inspect就有29次工具调用；改进方向是先读已知配置和结构化结果，再查询缺失字段，不能编造“8分钟”或把工具等待算为追迹。新版指令是否降低耗时仍需之后的DSH+GLM实测。

测试会话列在“未分组”，因为创建只传cwd未传workspaceId。原生轨迹证实N06的AGENTS.md与项目Skill已加载，所以未分组不等于没项目环境。未来测试用官方workspaceId建会话（该API与cwd二选一），再核对实际规则/技能注入；UI分组、工作目录和规则加载分别验证。
