# 原则：规模分档、任务分级与默认约束

本文件展开 instructions.md 中“规模分档”“按任务分级”“可检查的约束”三节的判定方法。三者正交：**档位**看项目，决定结构下限；**级别**看本次任务，决定流程轻重；**约束**是随时可用的判错规则。

## 项目规模分档

先定档再定结构。档位不确定时取较低一档，写明“出现哪些信号就升档”。

| 档位 | 识别信号 | 最低要求 | 不需要做的事 |
|---|---|---|---|
| 一次性脚本 | 跑一次或几次即弃；只服务当前任务；无人依赖其输出格式 | 参数、路径、阈值集中在文件顶部常量或命令行参数；放项目规定的 scratch/temp 位置；文件头一行注释说明用途与日期 | 不分模块、不写测试、不建配置文件、不加日志框架、不进正式包 |
| 小工具 | 反复使用；单人维护；一个入口；代码约数百到两千行 | 入口（参数解析与装配）/ 核心逻辑 / 配置三分；核心逻辑可在不碰磁盘网络的情况下调用；一条运行命令写进 README | 不引入插件系统、DI 容器、抽象基类层级、多环境配置矩阵；不为“以后可能”拆包 |
| 长期项目 | 预期维护数月以上；多个入口或多个子功能；有外部用户或下游 | 明确分层与依赖方向；配置集中且有样例；IO 在边界层；有测试入口和一条统一校验命令；ARCHITECTURE.md 写“新增 X 放哪里” | 不强制六边形/DDD 全套；不为每个类配接口；不要求 100% 覆盖率 |
| 多人/多 Agent 系统 | 多人或多个 Agent 并行改；跨会话持续开发；模块所有者不同 | 在长期项目基础上：分层边界由工具判失败（import-linter / dependency-cruiser / CMake 目标）；`.agents/architecture.toml` 声明 layers；重大取舍写 ADR；公共能力只有一个归属模块且写进对照表 | 不为每个模块单独仓库；不在没有冲突证据前引入代码所有权审批流程 |

升档信号：同一段逻辑第二次被复制；出现第二个入口；有人开始依赖输出格式；第二个人或 Agent 开始改它；单文件超过约 400 行仍在增长。降档同样合法：长期项目里的探索脚本按一次性脚本对待，只要不混入正式模块。

## 任务分级 L0/L1/L2

档位与级别独立：长期项目里改一个默认值仍是 L0；小工具里新增插件机制则至少是 L2。

| 级别 | 判定信号（满足任一即可归入该级或更高） | 流程 | 产出 |
|---|---|---|---|
| L0 直接做 | 1–2 个文件；不新增模块、入口、公共接口、配置键；做法明确无取舍 | 直接实现 → 跑相关检查 | 交付时一句话说明落点 |
| L1 短方案 | 3–5 个文件；在已有模块内新增文件；新增配置键；改内部接口但调用方都在本模块 | 回复内给 5–10 行落点表 → 按授权确认或继续 | 落点表，不写计划文件 |
| L2 设计＋计划 | 新模块/子系统/入口；跨层或公共接口变更；新增依赖库；预计 >5 个文件；预计跨多轮会话；需要多人或多个 Agent 分工 | 分段设计并确认 → 写计划文件 → 按任务执行并逐项验证 → 对照方案自查；提交检查一次 | 设计摘要、计划文件、审查结论 |

判定步骤（30 秒内完成）：

1. 会动哪些文件？数一下，并看是否新建目录或入口。
2. 是否改变别人调用的东西（公共函数签名、CLI 参数、配置键、文件格式、HTTP 接口）？
3. 是否新增依赖方向（A 第一次 import B）或第三方库？
4. 做法是否唯一？有两种以上合理做法且代价不同 → 至少 L1。

**升级条件**：执行中发现需要新模块、新入口、改公共接口，或改动文件数超过原级别上限时，停下来说明并升级，不悄悄扩大。**降级**：L1 方案写完发现只动 1 个文件，直接按 L0 收尾。拿不准时取较低级别，同时写出升级条件。

流程细节见 `arch-plan` 技能；计划文件模板见 [templates/plan.md](templates/plan.md)。

## 默认可检查约束

以下与 instructions.md“可检查的约束”逐条对应，补充判定方法。项目配置另有规定时以项目为准；规则只在对目标有影响时适用。

### C1 单一归属

- **规则**：一项能力只有一个归属模块；一个需求通常只动一个模块，超过三个模块需在方案中说明原因。
- **判定**：按函数名、配置键、错误信息文本搜索，同一能力出现两处实现即违反。看最近几次改动：同类需求是否总要同时改多处。
- **证据**：`grep` 相近函数名（如 `load_config|read_config|parse_config`）；对比两处实现的输入输出。

### C2 依赖方向

- **规则**：上层可依赖下层，下层不 import 上层；无模块级循环；入口/CLI/UI 只做装配与参数解析。
- **判定**：`arch_scan.py` 的 `ARCH-LAYER`、`ARCH-CYCLE`；或成熟工具（[tooling.md](tooling.md)）。入口文件中出现循环、计算、格式转换超过约 30 行即视为承载了核心逻辑。
- **常见合法例外**：类型声明（Python `if TYPE_CHECKING:`、TS `import type`）不构成运行时依赖，但仍应遵守方向，否则说明边界划错。

### C3 配置与硬编码

- **规则**：路径、URL、主机、端口、模型名、阈值、密钥从配置、参数或环境注入；业务代码无本机绝对路径和凭据；常量命名并集中。
- **判定**：`ARCH-HARDCODE`、`ARCH-SECRET`；grep 线索：`[A-Za-z]:\\\\`、`/home/`、`/Users/`、`localhost`、`127.0.0.1`、`:\d{4,5}`、`api[_-]?key`、`token`、`password`。数值魔法值：同一字面量出现在两处以上且含义相同。
- **允许**：测试夹具中的固定样例数据；`[hardcode] allow_paths` 中声明的文件；协议规定的常量（如 HTTP 状态码）。

### C4 IO 与逻辑分离

- **规则**：文件、网络、数据库、子进程集中在边界层；核心逻辑能用内存数据测试。
- **判定**：核心模块中出现 `open(`、`requests.`、`fetch(`、`fs.`、`subprocess`、`std::ifstream`、`popen`；或其测试必须准备真实文件/服务才能运行。
- **最小改法**：把 IO 抽到调用方，核心函数改为接收数据或可调用对象（见 [patterns.md 端口与适配器](patterns.md#p2-端口与适配器六边形)）。

### C5 文件与入口

- **规则**：单文件 >约 400 行先考虑拆分，>约 800 行须给理由；新建顶层目录或新入口须说明为何现有位置放不下；一次性脚本与正式模块分开。
- **判定**：`ARCH-SIZE`、`ARCH-LAYOUT`、`ARCH-ROOT-SCRIPT`。行数只是信号：一个 900 行的生成表、协议定义或测试数据文件可以合理存在，写明理由即可。
- **拆分依据**：按职责拆（解析/计算/输出），不按行数平均切；拆后每个文件应能一句话说清职责。

### C6 公共接口

- **规则**：模块对外暴露最小接口；跨模块只经公开接口访问，不读写对方内部状态或私有文件。
- **判定**：Python 跨包 import `_private` 名称或深路径子模块；TS 从别的特性目录 import 非 index 的内部文件；C++ include 别的目标的 `src/` 或 `detail/` 头文件；任何模块直接读写另一模块的缓存/状态文件。

### C7 生成物与源

- **规则**：生成文件、构建产物、缓存不手改、不入源码目录；生成来源与命令写清。
- **判定**：文件头含 “generated / do not edit / 自动生成” 却出现在本次 diff；`dist/`、`build/`、`__pycache__`、`*.pb.*`、`compile_commands.json` 进了源码目录或版本库。

## 抽象准入

新增接口、基类、工厂、插件点、配置开关前，回答：

1. 现在有几个**真实**使用者？少于 2 个且没有已确认的近期需求 → 不加。
2. 去掉这层抽象，调用方要改几处？只改 1–2 处 → 不加。
3. 这层抽象能否被测试或工具验证？不能 → 它只是文档负担。

项目已有约定优先于通用最佳实践；不擅自大改既有结构。
