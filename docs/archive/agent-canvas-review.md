# AgentCanvas 初稿整体检查

日期：2026-09-26。范围：官方3080插件、3081适配、Canvas数据边界与固定DSH版本接口。状态：源码审查＋无副作用隔离探针；未修改运行实现，未连接/领取画板，未调用模型，未做浏览器视觉验收。

## 结论

当前官方插件是“固定聊天的投递探针＋通用画板页签”，尚未实现用户认可的“从当前聊天打开绑定画板并连续讨论”。3081有另一套定向接收实现，但不能代替官方聊天入口。用户报告的两个问题成立；其中入口已有右侧guide登记，不能说完全没有任何打开代码，但缺少当前聊天的明确入口和绑定动作。

## 发现（按优先级）

1. **P1：目的会话为全局静态配置，前端不参与绑定。** `plugins/optdsh-agent-canvas/lib/index.js:144`直接resume `cfg.dshSessionId`；`config/agent-canvas-bridge.json:3`指定单一会话。Client没有会话服务或绑定Remote。切到聊天B打开画板后，提交给该接收者仍会进入配置聊天A；未校验该聊天与画板项目关系。应由当前会话的显式操作建立并持久保存绑定。
2. **P1：没有画板身份，不能按会话恢复画板。** `lib/client.js:65`只加载4173首页，不带项目或画板身份；外链同样如此。Canvas恢复上次项目或临时画板，场景目前按项目保存。多个DSH页签即使外壳按session隔离，内层也没有独立board。原设计“每项目共享当前画板”不足以满足本轮提出的绑定画板体验。应引入boardId，默认一聊天一画板；跨聊天共享另作显式动作，不用伪项目目录模拟身份。
3. **P1：每次重新resume，未复用或释放现存Agent。** `lib/index.js:144–150`每次创建恢复句柄，丢弃dispose，处理后只whenIdle/flush。固定版本AgentRegistry拒绝重复注册同ID；resume还会打开持久会话写句柄。目标聊天已活动、或第二次画板提交时可能失败/等待写锁，不能视为连续协作。应使用官方会话输入服务统一获取/复用Agent，明确所有权，不释放Web持有的Agent。此项为固定版本源码推断，未在用户运行会话中主动制造冲突。
4. **P1：去重持久化仅写不读，requestId未参与交付。** `lib/index.js:66`每次初始化空processed，启动saveState覆盖此前记录；152生成requestId，160的followup没有传递该标识；180才在回答后记状态。隔离构造探针确认state.json从未被读取。应先持久记录交付状态，再使用上游支持的有身份入队路径；崩溃不确定窗口显示需核对，不自动重发。不能宣称已有可恢复幂等。
5. **P1：模型一轮结束就提前complete，且归属判定不可靠。** `lib/index.js:161–177`用whole-agent whenIdle以及最后turn/end认定当前提交完成；completed也可能只是向用户提问。DSH声明whenIdle不标识某条消息完成。该行为与3081的“用户确认处理完成”及项目协作Skill冲突。应把已回答与已处理分开，确认按钮绑定准确submission；失败的complete应单独重试，不能重跑模型。
6. **P2：界面缺少会话操作与真实状态。** Client仅注册tab类型和页签body（91–99），没有会话头部/输入区“打开绑定画板”按钮，也没有绑定查询、连接/断开、目标聊天名、交付错误或提交卡片。iframe onLoad直接ready（67），无法证明Canvas应用或接收通道健康；8秒超时只是展示逻辑。应分别呈现页面加载、画板绑定、接收等待和任务处理状态。
7. **P2：插件卸载取消没有贯穿正在处理的请求。** run的signal只控制循环；api仅用70秒timeout（90），cycle收到提交后不检查signal（124），whenIdle也没关联卸载。热重载/退出期间可能继续处理已领任务；插件effect只触发abort，没有等待任务收敛。应停止收件并等待清理，对已领取任务保存明确状态，不能把停止监听等同任务已取消。

其他边界：Host路径检查是字符串relative＋stat，未作realpath/Junction校验；与3081的Path.resolve边界不同。提交记录也缺绑定版本、sceneRevision和持久内容引用。以上应随桥接收敛补齐，不应让两套代码持续演化不同的验证和完成语义。

## 建议修订

- 会话拥有持久绑定：`workspaceId + dshSessionId -> boardId`；临时接收者ID是连接状态，不是画板身份。首次点击创建绑定，已有绑定直接打开；刷新/切换/重启恢复同一board。
- 官方会话头部提供始终可见的“画板”入口；展开右侧页签并显示当前聊天标题。Canvas嵌入需明确支持board/目标绑定协议，不仅加一个它不会解析的URL参数。
- 提交保存不可变快照：submissionId、boardId、sceneRevision、目标sessionId、说明与内容哈希。点击发送时冻结目标，之后切换聊天不改变归属。
- 一套Host桥接拥有状态机与模型交付；3080和3081只作为入口适配。现有两条后端若暂时保留，需使用各自明确标签与统一契约，禁止并发持有同一DSH写会话。
- 聊天记录显示画板提交卡片和版本；回答完成仍保留“确认已处理”。用户可从历史卡片打开历史快照，而非悄悄跳到最新图。
- 保留已有画板和历史提交。升级时将旧项目画板作为可导入/显式共享的旧画板，不自动复制到每个聊天，也不覆盖原始scene。

## 验收顺序

1. 两个聊天分别点击画板，得到不同board；切换回来及刷新后恢复正确内容。
2. 在A提交后立即切B，A收到提交和回答，B不受影响；接收目标在画板内明确可见。
3. A连续提交两次，及A已有普通对话运行时提交，均复用同一DSH会话并正确排队。
4. 同项目独立Canvas、3081与3080并存，不抢收件、不静默改项目、不共享未声明的草稿。
5. 入队前后/回答后/complete前重启，状态不丢、不重复推理；未知交付状态停下待核对。
6. 服务断开、取消、模型要求澄清均不误标processed；真实状态显示准确。

隔离探针输出：构造Bridge后processed为空、stateFileRead=false；Client只注册tab-type与sidebar.right.pane.tab，iframe URL为通用首页；followup不带已生成的requestId。探针使用内存mock，不代表浏览器或模型端到端验收。
