## 1. 核心结论

**现在是“代码按模块整理过的项目内运行平台”，还不是“全局安装的平台＋任意研究目录＋独立可选插件”。** 葱哥指出的问题有实际源码依据，不只是目录看起来杂。

| 希望达到的效果 | 当前判定 | 依据 |
| :--- | :--- | :--- |
| 平台独立安装，研究不必放在平台仓库 | 尚未实现 | 启动器固定仓库 cwd，DSH_HOME、Python、专家分发与运行状态均在仓库；自有插件限制会话 cwd |
| 自有插件统一放插件目录 | 已有目录归属 | 当前五个自有插件在 plugins/；公共光学包在 packages/optics |
| 插件独立发布、安装、开源 | 未完成产品交付 | 全部自有插件 private:true；主要使用源码路径加载；独立包配置与依赖契约不足 |
| 工作台可以不安装，也可以单独安装 | 尚未形成完整验收能力 | 平台 setup 无条件装光学环境；工作台静态依赖 Canvas 资源和 Forms 入口 |
| AgentCanvas 独立安装，DSH 仅做薄桥 | 外部编辑器已有独立发布，薄桥目标尚未完成 | 独立 Canvas 有公开预览安装包；DSH 插件仍实现通用画板存储、提交、建议稿与绘图规则 |
| 换机复现开发机的插件组合 | 目前不能靠拉代码达成 | 市场插件位于忽略的 profile，setup 不安装推荐列表，推荐文档已与现场清单有差异 |
| Windows 干净安装模拟测试 | 本机具备初步条件，但未启用/实测 | Windows 11 Pro、硬件虚拟化启用；Sandbox 功能 Disabled |

建议把重构的主要目标定义为**安装边界、数据边界、会话 workspace、插件契约及部署可复现性**。只把 STUDYS 移出去或只把仓库装到全局目录，无法解决下面的路径和会话限制。

读取了 README、planning/STATUS、架构/运行指南、推荐插件、根与相关模块 AGENTS、安装/启动脚本、插件 manifest、关键宿主/客户端源码、光学打包与执行入口；另只读查看 N05 AgentCanvas 的说明、manifest、发布与嵌入协议，没有修改相邻项目。

本轮证据分为：

- **源码已证实**：文件及条件直接存在。
- **局部探测已证实**：确实执行的只读查询或无服务小探测。
- **风险推断**：有依赖链依据，尚未启动独立安装环境复现。
- **待验**：新机、公司网络、许可证、真实业务执行等本轮未进行的验证。

没有运行全仓 npm test。它当前包含项目 Python、专家分发、DOM 等多类检查，且有测试写临时文件；本轮聚焦发布与目录边界，用更直接的小探测取证。旧状态文档里的测试通过不能作为本轮新机安装通过的证据。

├─ plugins/

好的基础值得保留：官方 DSH 由 npm 安装，没有另 fork 一套 Agent 循环；自有资源已有包归属；工作台通过 HTTP 调光学后端；会话仍走官方 sessionController；画板已有 revision、回执、冲突和 uncertain 状态。当前问题是这些模块尚未成为可独立安装、组合和迁移的产品单元。

“源码同处 monorepo”和“用户研究必须在平台源码中”是不同问题。以后可以继续在一个开发仓库维护多个包，也可以拆成多个开源仓库；**两者都应该允许从安装包运行并把研究 workspace 放在任意目录**。先确定包的边界，仓库数量可在方案阶段决定。

## 4. 五项主要架构问题

### 4.1 安装根、用户数据根和研究目录混为一个 ROOT

已证实的关键位置：

- `scripts/runtime/start-dsh.ps1:4-9`：从脚本定位仓库，官方 CLI、运行状态和日志均取仓库路径。
- 同文件 `:68-73`：启动前必须用仓库 `.venv` 运行专家分发，DSH_HOME 指向仓库 data/dsh。
- 同文件 `:91`：子进程 WorkingDirectory 固定为仓库根。
- `plugins/optdsh-workbench/lib/index.js:14-20`：ROOT 从 projectRoot/process.cwd 得到，会话 ownership 要求 cwd 精确等于 ROOT。
- 同文件 `:47-50`：列表只显示该 ROOT 的会话，新建会话也使用 ROOT。
- `plugins/optdsh-agent-canvas/lib/index.js:13-27`：同样只允许 ROOT 下的会话。

因此，官方 Web 能选其他工作目录，并不代表光学工作台与画板能在那个目录工作。即使把平台移动到一个全局目录，自有插件仍可能把那个安装目录当研究目录。

后续至少需要独立表达：安装目录（只放版本化程序）、Harness 用户数据目录、当前会话 workspace、当前光学实例/作业数据。全局可调用通常可以采用按用户安装，不一定要管理员级安装，也不应要求安装目录可写入研究数据。

多研究 workspace 不等于可以同时操作同一个 Zemax 实例：实例级串行化、身份/revision、锁与恢复仍要保持。不能仅按两个目录各建一把锁就认为共享实例安全。

### 4.2 插件“存在”与“可选”没有形成完整契约

`plugins/optdsh-workbench/web/workbench-agent.js:7` 静态 import `/api/optdsh-canvas/transport`，该资源由 Canvas 插件 `lib/index.js:40` 注册。工作台包没有声明 Canvas 依赖；Forms 的入口也直接出现在工作台页面。

**风险推断**：不装/停用 Canvas 时，工作台的 ES 模块依赖无法加载，可能阻断整页交互。这是明确的代码依赖风险，本轮没有停用正在使用的插件做浏览器复现。Forms 未装则有失效链接。

更深的一处反向耦合：平台启动等待 `.runtime/web-launch.json`，而认证启动记录由工作台 `lib/index.js:15-16` 写入。普通 DSH 启动的就绪机制与可选光学插件耦合，不应仅通过从 YAML 删除工作台来宣称可选化完成。

当前 setup 无条件创建 Python 3.12 环境并安装 optics。后续基础平台的安装/启动不能因为用户不需要光学功能而仍依赖 Python、Zemax 或专家开发资源。

目标是明确安装组合：纯平台、平台＋画板、平台＋工作台、平台＋两者；每种组合都有验收证据，缺少可选组件时给可操作提示，并保证已有功能正常。可选安装和运行时热卸载应分开验收，进行中的仿真/画板提交不能被无条件中断。

### 4.3 当前主要插件是私有 workspace 包，不是已交付独立插件

五个自有插件 manifest 均为 private:true。根 package workspaces 为 plugins/*，加载配置仍用 `../plugins/.../lib/index.js`。这适合开发，不足以证明包发布后能被独立安装和发现。

具体强假设包括：Canvas 必须读取宿主 `config/agent-canvas-bridge.json`；工作台视图读宿主 `package.json` 取得产品版本，新建聊天读 `config/optics-model.json`；专家包向上三层定位仓库，并读取专家生成目录。Canvas 与专家还直接 import DSH tools/subagent 等包，其宿主依赖应在独立发布契约中明确，而非只依靠大仓 hoisting 恰好可解析。

打包预检结果见第 7 节：有 files/exports 的包已能形成小型文件集合，但目前主要包都没有自身 bundle patch；本轮 tarball 清单没有 LICENSE 文件，根仓库也未找到 LICENSE。开源发布前需补齐清晰的许可与第三方声明、独立安装说明、支持的宿主版本、默认配置、数据归属及卸载策略。**去掉 private 并不能自动解决这些问题。**

市场化插件应声明 DSH 宿主兼容范围；Cordis peer 或某一个 DSH 内部库版本不能代替完整的宿主兼容验证。当前已知版本豁免应单独保存为用户选择，不能悄悄自动放行。

### 4.4 Canvas 已外置编辑器，但 DSH 侧仍有通用画板业务

独立 AgentCanvas 已公开 [v0.2.2 预览版](https://github.com/nefer5/AgentCanvas/releases/tag/v0.2.2)，现场公开 API 确认 draft=false、prerelease=true，有 Windows setup.exe、便携 ZIP、源码 ZIP 与 SHA256SUMS。README 与发布手册说明按用户安装，发布包不含 Node，需要用户具备 Node 20+。这是现成基础，本轮没有下载、安装或复测这些安装包。

注意：查询 GitHub releases/latest 返回 404，随后查询 releases 列表与页面确认存在预览版；不能把 latest 404 解释为“没有发布包”。

DSH Canvas 插件不仅做 iframe/消息转发，还拥有：

- `lib/boards.js`：BoardStore、持久化、提交、建议预览/应用/拒绝。
- `lib/drawing.js`：绘图对象规则、文字尺寸等业务。
- `lib/tools.js`：画板读取和建议工具。
- `lib/index.js`：会话绑定、工具装配、反馈投递与全局系统提示。

外部编辑器地址在 transport、client 与工作台 CSP 多处固定为 4173。独立 Canvas 换安装位置不一定影响 HTTP 地址，但换端口、未启动、版本不匹配等情况尚无完整发现与协商契约。

方案阶段应明确：通用画板文档、revision、历史、绘图操作、建议稿和恢复由谁拥有；DSH 桥接保留宿主认证、sessionId 绑定、工具适配、消息投递与 UI 挂载。薄桥仍可保存少量宿主关联和投递回执，关键是不要再复制通用画板引擎。

不能直接让 DSH 去消费独立 Canvas inbox：当前嵌入模式有意与独立 CLI 收件箱隔离，默认用户操作流程也不同。移动能力时必须保留唯一事实源与明确模式边界，并制定旧 data/canvas 和新 Canvas 数据的映射、哈希验证、失败恢复与可回退策略；不要复制成两个互相覆盖的 store。

### 4.5 公共光学后端与具体课题仍有实质耦合

光学源码已摆脱 N02 运行依赖，但“项目内独立”不等于“安装包独立”。

- `packages/optics/scripts/server.py:11-23` 和 mcp.py 从祖先目录找 AGENTS.md＋package.json，然后注入 packages/optics/src。
- 服务/worker 的启动仍使用仓库 scripts 位置。
- pyproject 包发现只包含 src，没有现有服务脚本的 console entry point；editable install 可用，不能据此证明 wheel 单装可运行整个服务链。
- `packages/optics/scripts/mcp.py:50-77` 读取仓库业务 Skill，并优先选 `STUDYS/2t2rLidar/configs` 下特定研究配置。
- Forms `lib/store.js:38-47` 通过 ROOT/STUDYS 枚举课题；对任意已打开外部研究目录尚无统一映射。

这部分也解释了为何仅移动 Study 不够：部分入口直接理解固定 Study 路径与平台布局。公共执行器应该消费显式研究配置、workspace 与 run 根；DSH 工具、Skill 的分发和发现是适配职责。2T2R 的术语与 H/V 契约要保留，但不应默认施加给所有新课题。

公司使用旧 Zemax 的兼容性是另一个维度。当前项目的 Python 连接链不能从本机新版本的成功推导为旧版成功；应按目标版本、运行时、DLL 加载、Extension 实例分别验证，必要时用独立进程隔离版本。此轮没有做 Zemax 连接或追迹。

## 5. 官方 DSH 方式：发布的核心是包、bundle 与 profile

官方 CLI 文档明确：运行命令所在目录是默认 workspace；profile 放在 `$DSH_HOME/profiles/<name>`，插件管理通过 `dsh plugin --profile <name> ...` 转发给 profile 内的 pnpm。[官方 CLI](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/README.zh.md)

官方架构将 profile 定义为组装与用户覆盖层，将 bundle 定义为带 patch 的可分发 npm 包；`dsh.profile.bundles` 记录有序组装，`dsh.bundle.patch` 指向包内 patch。[官方架构](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.zh.md) · [app-boot](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/boot/app-boot/README.zh.md)

本机 rc.2 的 home helper 明确支持默认 `~/.dsh` 以及 DSH_HOME 覆盖。本轮只调用路径解析函数，得到默认 `C:/Users/admin/.dsh` 和显式测试 home，没有创建 profile 或启动 DSH。

因此需要区分三种目录：

| 目录 | 用途 | 对目标的意义 |
| :--- | :--- | :--- |
| 自有开发仓库 plugins/ | 编辑、测试各插件源码 | 当前已基本做到，可继续 monorepo |
| `$DSH_HOME/profiles/<name>/node_modules` | 用户安装的插件依赖 | 官方运行时组织方式，随 profile 管理 |
| 独立研究 workspace | 模型、研究配置、结果、项目规则 | 应不要求存在平台源码与 node_modules |

没有找到“第三方产品必须把所有插件放在某个源码 plugins/ 目录”的官方通用要求。官方自身也按 packages 的职责分组；**目录名不是插件标准，独立安装、声明、发现、加载与卸载才是。**

未来 optDSH 可考虑成为官方平台上的可安装 bundle/产品组装，安装器或薄命令负责选 profile/版本/路径，不另 fork 官方 Agent 循环。是否提供独立品牌启动命令可后续讨论，但底层仍应调用受支持的 dsh profile 入口。普通全局 npm 安装一个包，也不等于已为 DSH profile 启用它。

## 6. 公司部署为何会缺插件，以及暂时不能归因的部分

### 6.1 “市场插件没有携带”有确定的机制解释

`.gitignore` 排除 data/；市场安装在 data/dsh/profiles/web 下。根 package-lock 管平台与自有 workspace，不能锁定这个独立 profile 的插件。setup.ps1 仅安装 Python/optics 和根 npm 依赖，不执行推荐插件安装。

本轮读取的 web profile 声明了 11 项外部依赖，其中包括 market、sidebar、theme、quote、context、GenUI、tasks 和语音相关包。**依赖存在、bundle 被选择、实际已加载、交互可用是四种不同状态**；本轮只核对清单，没有据此声称它们全部 live。

典型现场差异：推荐文档曾记录 dshmarket 1.66.5、Better Sidebar 0.24.1，而当前 profile 为 1.66.15 与 0.25.0，并包含后来新增的任务等插件。因此手工照旧文档安装，也不保证重现开发机。

正确方向应为显式、版本化的部署清单：产品必需包、用户选装包、可选推荐包分开；清单记录版本、选中/停用状态与已确认的兼容豁免；对应 profile 的锁文件或发布离线包验证完整性。目标机既有个人插件与用户设置需要保留，不拿开发机整个 data/dsh 覆盖。

### 6.2 环境隐含依赖会掩盖安装缺口

本机有 Node 24.13.1、npm 11.8.0、pnpm、PowerShell 7、py，以及个人 Agent 中心。新机可能只有 Windows PowerShell 5.1 或没有这些工具。setup 需要 Python 3.12 和 npm；市场安装还需要 pnpm。

当前 `.agents/experts/{software-architect,visual-designer}` 和部分开发 Skill 是指向 `C:/Users/admin/.agents` 的 Junction。它们是合理的开发环境组织方式，但不能直接作为独立产品安装依赖。启动器却必须执行专家分发，这使本机个人开发资源进入产品启动链。后续需发布可分发公共专家资源，把个人偏好、私人图片及本机 fleet 排除，同时明确未安装专家时平台的行为。

Canvas 独立服务、PPT 自有安装链、项目 Python、工具依赖都应逐项进入发布清单。不能用本机 node_modules、全局 PATH、Junction 和正在运行的服务给安装包补齐缺失内容。

### 6.3 公司“各种 bug”目前只能列调查入口

尚未拿到公司原始错误、安装包 SHA、OS/Node/Zemax 版本、代理/证书策略与启动诊断。本轮不能把全部故障归因于某一插件或目录。

现有状态文档记录过工作台 view 400、列表为空、PID/认证旧记录、客户端 slot 冲突、Python.Runtime 加载差异等。它们是后续回归种子，不等于公司同样出错。新报告应记录失败步骤、错误码、脱敏栈、组件版本和 workspace，避免“安装成功”一句话掩盖后续加载错误。

## 7. 本轮局部探测结果

## 8. Windows Sandbox 是什么，适不适合这里

可以把它理解为在本机快速打开一台临时 Windows：它用 Microsoft hypervisor 隔离内核，宿主已安装的软件不会自动成为沙箱内的软件；关闭窗口后，沙箱安装的软件和内部状态被清掉，下次启动重新开始。Windows 11 22H2 起，在沙箱内部发起重启可保留本次状态，但关闭沙箱仍会丢弃。[Microsoft Sandbox 概述](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/)

它非常适合检查“拿到发布包后，缺 Node/缺 Python/缺插件怎么办”“全新 profile 能不能装”“是否偷用了开发机资源”。它与 Agent 的文件权限沙箱、Python venv、DSH shell sandbox 不是同一层；这些工具不能替代干净 Windows 安装测试。

### 8.1 本机实测条件

| 项目 | 本轮读回 |
| :--- | :--- |
| Windows | Microsoft Windows 11 专业版，64 位，10.0.26200 |
| 处理器 | AMD Ryzen 7 9800X3D，16 逻辑处理器 |
| 内存 | 约 93.7 GiB |
| BIOS 虚拟化报告 | VirtualizationFirmwareEnabled=True |
| HypervisorPresent | True |
| Windows Sandbox 功能 | Containers-DisposableClientVM=Disabled |
| 完整 Hyper-V 功能／管理 PowerShell | Disabled／Disabled |
| VirtualMachinePlatform | Enabled |
| HypervisorPlatform | Disabled |
| C/E 空闲盘空间 | 约 66.2/1059.6 GiB；瞬时值，不是容量承诺 |

CPU 的 SLAT/VMMonitor CIM 字段读到 False，而机器已报告 hypervisor 存在。仅凭这些字段不作“不支持虚拟化”的判定；**目前结论是版本、资源和虚拟化迹象符合初步条件，最终能否启动仍须启用后验证。** 不把 vmcompute 正在运行等同 Sandbox 已启用，也不把 HypervisorPresent 等同完整 Hyper-V 管理器已安装。

微软要求支持的 Windows 版本、BIOS 虚拟化、至少 4GB 内存、1GB 空闲磁盘与两个核心。启用是持久系统变更，可能需要管理员及重启，本轮没有执行。[安装条件与启用步骤](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-install)

### 8.2 三类测试环境的分工

| 方式 | 建议用途 | 局限 |
| :--- | :--- | :--- |
| 独立目录＋独立 DSH_HOME/profile | 快速验证路径与插件组装 | 仍共享本机 PATH、工具、网络、个人中心，不能当新机 |
| Windows Sandbox | 每版发布包的干净安装冒烟；缺依赖/插件组合/路径测试 | 不适合长期保存环境；不是任选 Windows/Zemax/公司网络镜像 |
| 持久 Windows 虚拟机＋检查点 | 固定目标 OS/工具组合，反复修复、升级、恢复、长流程 | 需要镜像、存储和相应授权；许可证与设备能力仍要验证 |
| 公司真实机器 | 网络出口、企业证书、安全策略、许可证与真实光学验收 | 本地无法完整替代 |

Hyper-V 可以创建不同 guest 系统，并用检查点恢复先前状态，因此更适合保存“纯 Windows”“基础运行时已装”“旧版 Zemax 待连接”等重复基线。检查点不是完整备份。[Hyper-V 概述](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/overview?pivots=windows) · [检查点](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/checkpoints)

资源建议属于方案估算：Sandbox 可先分配 8–16GB 用于 npm/构建及 UI 冒烟；完整 VM 可从 4–8 vCPU、16–24GB RAM、80–120GB 动态磁盘试起，按 Zemax/构建负载调整。当前 C 盘余量不适合盲目堆完整 VM，可考虑 E 盘存 VM。**这些不是官方最低要求，也没有创建或性能实测。**

### 8.3 Sandbox 能发现与不能代替的验证

可发现：依赖未列、Python 版本假设、相对路径、安装目录可写假设、Junction 缺失、插件包漏文件、插件宿主范围、Canvas 未安装、单独工作台的模块加载、第一次启动/重启、中文空格路径等。

不能自动复刻：公司代理认证、TLS 企业根证书、域策略、杀软控制、内网源、模型地域限制、硬件加密锁/许可证服务器，以及 GPU 性能。沙箱里的 127.0.0.1 是沙箱自身；不能让沙箱光学客户端误以为连到了宿主的 3081/4173。默认网络也不能当“与公司网络一致”。

光学 UI/协议建议先用明确标识的 synthetic backend 验证安装与数据链，再在获许可的完整 VM 或公司机器测试目标 Zemax。Synthetic 通过不能证明真实求解、收光效率、串行化或旧版 API 兼容。

### 8.4 可重复的沙箱测试流程（候选，未执行）

1. 准备实际发布包与 SHA、固定版本安装源，避免映射整个源码仓库或现役 node_modules。
2. 发布输入目录只读映射；另设空的专用输出目录可写映射，用来保留日志。不要映射个人凭据和完整 DSH_HOME。
3. 把包复制到沙箱内部安装路径再执行安装；只读映射目录本身不是正常安装目录。
4. 沙箱内部独立安装依赖、建立测试 home 和两个研究目录，检查未依赖宿主服务或个人中心。
5. 运行无真实模型/无 Zemax 的安装、HTTP、模块及 synthetic 冒烟。
6. 导出脱敏结果、组件清单、日志、哈希和失败截图；关闭沙箱，再重新开一轮复现。

`.wsb` 是 XML，可指定内存、网络、vGPU、目录映射与登录命令。建议未来提供联网安装和离线包两种配置，日志映射明确可写；需要 WebGL 时另验 vGPU 与软件渲染，不把 vGPU 当 CUDA/真实显卡验证。[微软配置说明](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file)

联网安装成功只证明相应下载来源可访问；离线测试需要事先完整提供 transitive npm 依赖、Python wheels 和必要运行时。只有四个插件 tarball 不构成完整离线部署包。LogonCommand 也不能使沙箱内测试自动成为“普通非管理员用户安装”证明，这一权限场景最好在完整 VM 中单列。

## 10. 发布包中的说明与 Archify 要求

发布包应让目标机用户或 Agent 不依赖开发者口头补充即可安装与排障：

| 文档/清单 | 内容 |
| :--- | :--- |
| 快速安装说明 | 系统/权限/运行时要求；在线/离线；验证第一步；无研究数据示例 |
| 架构说明 | 官方 DSH、自有 bundle、Canvas、光学 backend、研究 workspace 的职责与依赖 |
| 插件操作 | 单独安装、启用/停用、版本范围、必需与可选关系 |
| 使用说明 | 任意目录打开课题、选实例、画板协作、保存与 run 输出 |
| 数据/迁移说明 | 安装/用户/项目/临时数据分开；保留、升级、回退、恢复与映射 |
| 排障说明 | 缺依赖、profile 不一致、插件 skipped、认证、端口、DLL、Canvas 握手 |
| 版本及完整性 | release 版本、DSH/插件组合、依赖锁或离线清单、SHA、已验矩阵 |
| 来源与声明 | 开源许可、第三方资源、未签名及预览状态、未覆盖验证范围 |

Archify 本机 doctor 已通过，适合后续制作可独立打开的交互 HTML 架构图。至少需要产品总览、安装/数据边界，以及一次研究请求与画板提交流程；不建议把所有关系挤成一张不可读大图。

需要保留源 JSON、HTML、校验回执、浏览器证据，必要时导出静态 SVG/PNG。图内必须区分“现状、候选、已实现”及“可选/必需依赖”，图与权威文档同步。严格校验和浏览器通过不等于美观，需要实际视觉检查，不能只报工具成功。

**本轮没有制作图，也没有开始界面设计。** 用户要求的是重构后的发布包图；待架构方案确定后再制图，并按项目规则在开始视觉设计前确认是否调用视觉专家。本轮无需因此阻塞调研。Archify doctor 是工具预检，不是最终图形验收。

## 11. 方案阶段的建议顺序与尚缺输入

这是基于调研的候选顺序，不是自动实施授权：

1. 先明确安装根/用户 home/workspace/实例作业的四种身份及数据路径契约。
2. 确定官方平台＋optDSH bundle 的产品形态、默认插件与选装组合，解除启动器对可选插件和个人专家中心的依赖。
3. 明确 Canvas 独立产品与 DSH 桥的能力、状态及迁移协议；同时消除工作台对 Canvas/Forms 的隐藏依赖。
4. 确定光学 backend 可安装入口、服务/worker 生命周期、版本适配及显式研究配置输入。
5. 制作插件发布产物和部署清单，再做干净 Windows 验收；最后同步安装说明与 Archify 图。

优先避免“大迁移以后才发现不能安装”。可先定义最小发布验收：基础平台＋两个外部 workspace＋工作台单装＋Canvas 单装。重构保留历史研究 run、现有用户配置和商业模型，不为新目录名重写历史报告。

后续方案还需要公司 Windows/权限、网络出口、Node/PowerShell/Zemax 版本、许可证形式和失败日志；这些是当前事实缺口。还有一个产品决策需要届时讨论：独立 Canvas 是否是通用画板数据权威，或以可复用核心包形式让宿主保存数据。两者都可做，但影响桥接厚度和迁移成本，不能在本轮替用户拍板。

## 12. 下一阶段完成标准

新机只拿发布包和明确的前置条件，就能安装平台和所选插件；无需 N06/N05 源码 checkout、个人 Agent 中心或开发机 data。平台安装在一个位置，研究目录可在另一个任意位置，两个研究会话的画板、配置与结果不串用。未安装光学/画板不阻断基础平台，单装工作台不因可选画板缺失而失效。

这组标准应同时体现在代码接口、安装器、文档和干净环境结果中。Sandbox 可以承担第一道安装验证；真实公司策略和 Zemax 的最终验收必须另列，不能用本机模拟代替。
