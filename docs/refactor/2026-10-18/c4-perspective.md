## 1. 用户确认的分析偏好

用户有小型项目开发经验，重视 Agent 应用时代对系统上层的把控：系统边界、职责分工、模块协作、可替换性、数据与权限归属、部署和演进。后续架构讨论优先使用 C4 的前三层组织分析：

- **C1 系统上下文**：这个产品为谁解决什么问题，与哪些外部系统交互，负责到哪里。
- **C2 容器**：哪些部分是可运行应用/服务或数据存储，如何通信，怎样安装、隔离、恢复。
- **C3 组件**：某个应用内部如何划分职责、公开接口与依赖，映射到哪些可发布包和源码模块。
- **C4 代码**：类、函数、内部实现不作为默认面向用户的重点；只有用户要求，或接口、并发、身份、恢复等关键约束必须深入时才展开。

这里的“代码层按需”是展示重点，不表示实现者可以省略源码检查、测试或安全门禁。也不要求每次固定出三张图；简单问题保持原 L0/L1 流程，复杂系统按实际问题展开必要视图。

## 2. 对本项目如何使用 C1–C3

| 层级 | 要回答的问题 | optDSH 的分析对象 | 需要避免的混淆 |
| :--- | :--- | :--- | :--- |
| C1 | 产品边界与外部依赖是什么 | 用户、optDSH、模型服务、Zemax；独立 Canvas 是否按外部产品观察需明确 | 画在同一电脑上不代表属于同一产品；近似视图不等于求解器 |
| C2 | 谁独立运行，状态保存在哪里 | 浏览器应用、官方 DSH 宿主、光学执行服务、独立 Canvas 服务、相应数据存储 | Container 不专指 Docker；npm 包、进程、源码目录不是一一对应 |
| C3 | 选定宿主内部有哪些职责 | 以 DSH 宿主为例：会话绑定、画板宿主适配、光学代理与可选能力装配 | 工作台 UI 与宿主适配可能在不同运行环境；不可把全部插件都冒充独立服务 |

每一张正式分层图要注明观察范围、现状/目标、外部组件和证据。原先的 architecture 总览混合了若干运行与模块层次，可继续作总览，但**不能仅因有一张总览就声称 C1、C2、C3 已分别完成**。若后续要求完整分层交付，应从同一组模块和关系展开，并与真实实现核对。

## 3. 三种关注视图与五种图型的关系

C4 是观察层级；运行关系、源码组织、安装数据布局是关注角度；Archify 的 architecture、workflow、sequence、dataflow、lifecycle 是表达方式。三者不相互替代。

| 用户关注 | 表达方式 | 与 C4 的联系 |
| :--- | :--- | :--- |
| 产品、应用与模块怎样协作 | C1/C2/C3 结构图 | 同一系统逐层放大 |
| 一个请求怎样完成 | 时序或动态视图 | 为选定层级补充关键场景 |
| 新机安装、失败处理、升级回退 | 流程图与部署视图 | 连接结构选择与实际环境 |
| 数据由谁读写，谁是权威 | 数据流图和归属表 | 补充静态结构未充分表达的信息 |
| 模块对应哪个包/文件目录 | 源码目录树、职责依赖对照 | 帮助 C3 落到实现；目录树不等于 C4 代码视图 |
| 作业的取消、失败与恢复 | 状态图 | 仅对重要生命周期按需补充 |

Archify 用于关系与行为表达，不限定唯一工具；文件树采用原生目录表达更直接。图形/引用/浏览器检查通过，不等于设计合理、独立安装成功或真实光学验收。

## 4. 重构讨论应优先审阅的内容

1. **职责与边界**：官方 DSH 会话循环保留；平台、插件、光学执行器、Canvas 产品和具体研究分别拥有明确职责。
2. **运行与交付单位**：区分插件、Bundle、Profile、进程、安装包和源码仓库。独立包不强制独立进程；单仓开发也可以独立发布。
3. **数据与权限**：区分安装根、DSH_HOME、workspace、Canvas 文档根和实例状态根；普通画板操作不授予 Zemax 写权限。
4. **关键场景**：纯平台、工作台独装、Canvas 独装、共同安装、两个外部研究目录、同一 Zemax 实例并发、迁移及新写入后回退。
5. **取舍与证据**：列出推荐方案、备选、代价、已知风险与未决项；严格区分历史实测、当前源码、目标设计和待验证能力。

这套方法服务于用户理解与决策，不新增固定出图数量、审批回合、自动扫描或模型调用。已有授权继续有效，具体实施仍以主任务授权为准。
