# 运行包规范

适用于本项目所有产生正式分析、评测或仿真交付的Skill和脚本。仅打印帮助、交互式预检与服务日志不强制创建run。公共实现为`packages/optics/src/optdsh_optics/run_bundle.py`，不依赖Zemax或DSH。

## 目录与命名

```text
runs/<workflow>/YYMMDD-NN/
  manifest.json        身份、时间、状态、来源、文件SHA-256
  config/input.yaml    原始输入配置，保留原格式（旧JSON输入为input.json）
  config/resolved.json 本次实际使用的完整参数
  config/runtime.json  必要运行环境字段（如适用，不含凭据）
  plan.json            工况计划（如适用）
  report.html          复杂任务必需；简单任务可用report.md
  result.json          机器读结果，失败也保留
  *.npz                大数组；按实际需要采用子目录
```

workflow使用tx、rx、baseline等短名。日期取分配时本地日期，序号至少两位、同一父目录递增，排他创建、不覆盖。开始只分配一次，所有阶段接收同一目录；不再嵌套时间戳或重复workflow。完整时间含时区，任务描述写manifest，不拼进目录。仓库相对路径按UTF-16计数，>180警告，>220拒绝，包含文件名。

具体研究使用`STUDYS/<study>/runs/<workflow>/YYMMDD-NN/`；平台验收仍可使用根runs，均采用同一公共分配器。

Study配置自动归属：当source配置位于STUDYS/<study>/下且未显式--runs-root时，新run写入该Study/runs/<workflow>/YYMMDD-NN。历史run内容保持不变；经用户明确指示可整体迁移，须保存路径映射并验证文件哈希。

## 配置与证据

- 配置型Skill遵循[铁律OPT-14](rules.md#opt-14-skill配置范式)：优先YAML，Skill包内附带YAML样例。run保留输入原文和扩展名；规范化resolved快照可用JSON。Tx入口已支持YAML及旧JSON；run保留原始扩展名，实际参数统一保存为resolved.json。

- 先冻结配置，再执行；执行器消费run中resolved配置。后续修改项目config不改变旧run。
- 文件输入同时保存原始配置和已展开默认值/覆盖值的resolved配置；只有CLI参数的工具也保存完整解析参数。清晰区分业务配置与运行环境，不能只记录外部文件路径。
- 输入数据能随包携带时保存副本并核对哈希；商业模型/大型外部依赖可只保留身份、版本、哈希和获取条件，明确包不独立可复现。活动模型的dirty内存不等于磁盘版本。
- 凭据不随包复制。运行环境采用允许字段清单，记录凭据名称或位置，不保存值。run默认Git忽略，不等于允许存放秘密。
- 完整执行代码以提交版本或代码文件哈希记录；哈希用于识别，不代表已打包全部依赖。缺失信息写unknown，不用当前代码/配置补成历史事实。
- 成功、计划、失败、未完成、历史整理分开标记。失败时保留已冻结配置、已完成工况与错误。强制杀进程可能留下created/running，不能当成功。
- 完成时manifest列出包内文件大小和SHA-256（不递归哈希manifest自身）。完成后不覆盖；更改参数重跑创建新run，续跑仅在工作流明确支持时使用。

## 报告分级与内容

- **十分简单的小任务可用Markdown**：如单项参数核对、简单配置检查、无多工况/图表的短结论。使用`report.md`说明任务、关键条件、结果、限制和证据即可，不为小任务强做HTML。
- **较复杂任务必须HTML**：如多工况公差、参数扫描、补偿前后对比、多步骤试验、模型评测、需要图表/多份证据才能解释的分析。复杂度由任务内容决定，不靠字数或耗时；Tx多工况和正式模型评测按复杂任务处理。拿不准时用HTML。
- 正式运行的配置冻结、结果、manifest及SHA-256要求不因Markdown而省略。manifest.report指向实际交付文件。交互式一句预检仍可仅输出JSON，不强制新建run。

HTML正文顺序必须是：**研究背景与目标 → Setup → 结果与解释 → 限制、证据与下一步**。开头可列身份、日期、实测/模拟/计划状态，但不以结果数字或配置原文代替研究背景。

1. 背景：为什么做、研究对象、要回答什么问题；说明范围及判定标准。未提供的业务条件明确待补，不能编造。
2. Setup：以参数表/摘要呈现所用模型及输入文件、版本、关键对象、坐标与单位、扰动/补偿、光源/波长、光线数/随机种子、探测面/采样、指标定义等与本任务相关的条件。只挑关键项，不把config原文直接贴在正文；缺失记未记录，不能用当前配置补历史事实。
3. 结果：关键指标、工况对照和必要图表；随后解释物理意义、分辨率/采样限制和是否达到目标。失败保留已完成部分，不用completed替代正确性判断。
4. 证据与后续：结果数据、配置快照、manifest和校验链接；明确下一步。**原始配置、完整解析参数、运行环境详情和完整结果JSON默认折叠**，正文不以JSON块代替专业解释。

HTML须UTF-8、离线无CDN、桌面/窄屏可读，随整个run移动仍可用（内部相对链接）；图表标单位、基准、统计口径。用户文本转义，原始JSON/CSV/NPZ保留为证据。样式与内容扩展规则见[光学报告指南](runs-and-reports.md)，视觉参考为[合成光学样例](../packages/optics/examples/report.html)。

公共实现`RunBundle.create(..., complexity='complex')`默认HTML；明确简单任务可用`complexity='simple'`生成Markdown，也可显式要求HTML。复杂任务拒绝Markdown，多工况结果不能以简单Markdown输出。`config.report`记录背景/目标/重点条件，`result.report`记录解释/后续；字段见报告指南。

具体分析命令和领域约束由业务Skill维护，研究配置与结果入口放Study；平台文档只规定通用运行包和报告格式。

# 光学运行与试验报告

与[运行包规范](runs-and-reports.md)配合使用。十分简单的小任务允许Markdown；多工况、多步骤、对照分析、模型评测等较复杂任务必须HTML。报告帮助读者理解光学问题与证据，不是配置文件查看器。

## 内容顺序

1. **研究背景与目标**：业务问题、对象、研究动机、范围和希望回答的问题。不能先贴结果卡片或config。
2. **Setup**：文件/模型身份与版本、输入来源、光学对象、光源/波长、坐标单位、扰动或补偿、采样、指标口径，按实际任务挑重点。没有记录就明确未知，不填想当然的默认值。
3. **结果与解释**：指标卡片/图表/表格，说明物理意义、精度限制、异常样本、是否可下结论。复杂内容可分章节或多个相对链接页面，不强套固定四页布局。
4. **证据与后续**：限制、可执行下一步、输入与数据链接。原始配置、完整解析参数、运行环境详情、结果JSON默认折叠。

Markdown最小结构为任务与关键条件、结果、限制、证据链接；可不做视觉包装。公开或提交前核对是否包含商业模型路径等不应外发信息，凭据从不进入run。

## 对象与表面标签

遵守根AGENTS的对象引用格式。正文、Setup、图表标题、表格和摘要统一显示`OBJ编号[Comment]`或`SURF编号[Comment]`。从同次run的检查证据或经过身份校验的冻结配置取备注，不查询当前模型来补历史报告。空备注用`[无 comment]`；未记录用`[comment未记录]`，两者不可混淆。计划的预期备注仍属于待核对配置。

公共标签函数为`packages/optics/src/optdsh_optics/object_labels.py`；HTML呈现须转义备注，机器数据可保持编号/comment独立字段。原始JSON/CSV字段名与稳定工况ID不改写，但人类可读标题须带完整标签。

## 视觉与排版

借鉴`E:/AgentTyvate/docs/templates/test-report.html`的米白纸张、深绿标题、统一中文无衬线字体、章节编号与折叠证据。该项目仅只读参考；本项目重新实现样式，不复制Skill评测案例或数据。固定参考：[光学报告合成样例](../packages/optics/examples/report.html)。

- 内容宽度约1192px，正文15px/1.85行高；主标题34px，章节标题21px。数字使用等宽数字字体，单位与统计口径靠近指标。
- **数据表格统一左对齐**：表头、行标题与所有数据单元格（包括数字、百分比和单位）均靠左排列，同列保持一致。禁止表头靠右而下方数据靠左，也不为数字列单独设右对齐。HTML统一使用`th, td { text-align: left; }`，不得被`.number`、列选择器或内联样式覆盖；Markdown表格同样使用左对齐列。
- 背景先行；Setup双列参数摘要在窄屏转单列。结果表仅在自身容器横向滚动，不让整页溢出。
- 米白/深绿用于层次，琥珀色标限制。不要只用颜色表达成功/失败或模拟/实测状态。
- 顶部章节导航、明显的编号标题带、键盘焦点、原生details折叠；无CDN、外部字体或必需JS。报告独立离线可读。
- 打印时保留正文、Setup和主要结果，隐藏导航及原始参数折叠区；不是完整原始证据归档，证据仍随run保存。

## 写入实际报告

公共生成器为`packages/optics/src/optdsh_optics/reporting.py`，样式为同目录`report.css`；CSS内嵌到产物，移动run不依赖源码。`run_bundle.py`负责分配/冻结/清单，不再内嵌大段页面样式。

在冻结的业务配置中添加可选`report`元数据（无需更改仿真数值）：

```yaml
report:
  title: Tx镜片装配误差分析
  background: 说明此次研究的实际背景和分析对象。
  objective: 说明希望回答的问题与判定条件。
  setup:
    光源波长: 由实际配置或测量记录填写，不猜测
    机械约束: 由已确认装配分组填写
```

`setup`只放精选标量文字，不贴嵌套配置。模型文件来自实际runtime.expectedFile；历史包没有保存则标未记录。对象、探测采样、追迹设置等由冻结配置提炼，不从外部最新config读取。

计算完成后在`result.report`中提供`summary`（结论）、`interpretation`（解释）、`nextSteps`（字符串列表）。缺失时生成器只给保守提示，不编造物理结论。模板/模拟/计划与真实结果必须分别标记。

十分简单的独立工具可调用`RunBundle.create(..., complexity='simple')`生成`report.md`；多工况默认HTML。现有Tx、基线分析入口保持HTML，简单任务允许MD不意味着把它们统一降级。

## 制作与验收

冻结本次参数 → 填背景/关键Setup → 运行并解释结果 → 生成报告 → 浏览器查看桌面与窄屏 → 检查导航、折叠、表格、证据链接 → 核对manifest哈希。历史run保持原样，重排历史报告应分配新包并说明未重新执行。

`python scripts/maintenance/build-report-example.py`用`examples/report-optics.synthetic.json`生成新的合成run并刷新固定视觉参考；该脚本不连接Zemax。样例只用于样式/内容结构，不代替真实验收报告。
